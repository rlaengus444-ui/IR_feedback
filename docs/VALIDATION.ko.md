# 외부 IR 모듈 검증 기록

검증일: 2026-10-27. 대상은 별도 실행하는 Windows 64비트 외부 모듈입니다.

## 구현 범위

- M1/S3 실행 창을 검색하고 명시적으로 연결/연결 해제합니다.
- 원본의 T_Recoating 표에서 새 기록을 읽은 뒤 Excel 수식으로 공통 IR 설정을 계산합니다.
- 실제 적용 모드에서는 기존 Sequences의 IR 입력과 Save만 사용합니다.
- 연결 준비 후에는 다른 탭·최소화 상태를 유지한 채 표 갱신과 IR 저장을 수행합니다.
- 저장 후 UI 표시와 기존 JSON 설정을 함께 확인합니다. IR 이외 owner 설정도 대조합니다.
- 직접 장비 통신, 프로세스 주입, 히터 ON/OFF, 자동 운전 시작/중단 명령은 구현하지 않습니다.

## 수식 재현

Notion의 `IR_출력제어_수동테스트_랜덤패턴_80층.xlsx`에서 추출한 저장 결과와 비교했습니다.
랜덤 80층 × 55열 = 4,400개, 입력 예시 67행 × 55열 = 3,685개로 총 8,085개 결과가 일치합니다.
비교 허용 오차는 절대 1e-9, 상대 1e-10입니다. 수식의 재현을 검증한 결과이며 실제 장비의 열 응답 검증을 의미하지 않습니다.

원본 파일 SHA-256: `2dbdff1057ab0a2f0bbe539b77ffb71782f10daf61f8d111236d6f5585e16a94`

## 자동 검사

GUI·세션·알고리즘·UI 어댑터·저장 파일 검증·미저장 편집값 검사의 **75개 테스트가 통과**했습니다. 숨김 GUI와 자체 시험 데이터를 사용했고 원본 장비를 제어하지 않았습니다.

별도 Windows 시험 창에서 실제 제품 `WindowsUiAdapter`를 그대로 사용한 8개 시나리오도 통과했습니다. M1/S3 정상 저장, 저장 응답 지연, 늦은 실제 저장, 입력 변경 중 지연, 입력 직후 AUTO→IDLE, M1/S3의 기존 미저장 편집값을 검사했습니다. 정상 저장은 1회였고, 저장되지 않아야 하는 경우에는 0회였으며 기존 미저장 편집값을 보존했습니다. 결과가 불확실할 때 두 번째 저장은 거부했습니다.

추가로 원본과 같은 104px 행 높이, 1,000행 가상 표, 표시 영역 ±128행 캐시 조건에서 초기 화면 0행부터 858층(인덱스857)을 찾았습니다. 해당 행의 T42를 읽어 IR67을 한 번 저장했고 모든 non-IR 값이 유지됐습니다. 이후 native 조회/heartbeat도 통과했습니다. 초기 ID 확인을 포함한 전체 사이클 시간과 단계별 시간은 `late-layer-results.json`에 기록했습니다. 센서 수신부터 램프 반응까지의 시간을 측정한 시험은 아닙니다.

초기 화면 조건 4개도 별도로 통과했습니다. WebCam 화면에서 시작한 M1/S3는 Sequences로 이동해 정상적으로 1회 저장했습니다. 이미 Sequences에 미저장 편집값이 있는 M1/S3는 재입장·Load·Save 없이 거부했고, 편집값과 기존 화면을 보존했습니다. 이 검사는 `bootstrap-results.json`에 기록했습니다.

## 다른 탭·최소화 개선 검증

원본의 `LayerInfoTable`은 화면을 숨길 때 타이머를 중단하지만, Scroll 이벤트는 `UpdateUI → ReadSnapshot/ReadRows`를 실행합니다. 외부 모듈은 숨겨진 표에서 한 행 이동·복귀를 제한 시간 안에 처리하고 실제 스크롤 위치의 변화·복귀·범위를 확인합니다. 완료되지 않으면 캐시값을 새 관측으로 사용하지 않습니다. 기존 화면의 활성화·복원·포커스 변경은 하지 않습니다.

숨겨진 WinForms 버튼은 `BM_CLICK`을 무시하는 것을 자체 시험 창에서 확인했습니다. 따라서 이미 식별·검증한 Save 버튼의 부모에 표준 `WM_COMMAND/BN_CLICKED`를 한 번 게시하여 기존 버튼 Click/Save 핸들러를 사용합니다. 버튼 클래스·MSAA 역할·부모·PID·Enabled 전체 경로를 확인하고, IR 입력 전과 Save 전에 현재 층·온도·AUTO 상태를 다시 검사합니다. 다른 필드와 owner 파일은 전후 대조합니다. 초기 AutomationId 확인 이후에는 입력/Save 때 UIA를 다시 초기화하거나 탭을 전환하지 않습니다.

실제 제품 어댑터를 사용한 추가 15개 시나리오가 `background-results.json`에 있습니다. M1/S3 각각 WebCam·Sequences, Process 최소화, WebCam 최소화, Sequences 최소화의 10개 조합을 검사했습니다. 연결 당시 최소화, 1,000행의 후반 층, 숨겨진 Sequence 미저장 편집, 검증 직후 층 진행, 스크롤 없는 표의 거부도 검사했습니다. 원본 형태의 별도 캐시는 숨김·최소화 동안 타이머 갱신을 멈추고 내부 온도만 변경했습니다. 같은 행의 42→53 변경과 새 층의 43 수신을 모두 확인했으며 활성 탭·최소화 상태를 보존했습니다. 저장 허용 시 1회, 미저장 편집·층 진행·갱신 불가 시 0회였습니다.

검증 직후 층이 진행되는 경우에는 과거 행의 온도가 여전히 남아 있어도 잘못 저장하지 않아야 합니다. 시험 창은 실제 표처럼 이전 층 기록을 유지합니다. native 도우미 안에서도 입력 직전과 Save 직전에 기존 로그의 최신 층 번호를 다시 읽어 이 경합을 검사합니다. 로그는 온도 입력에 사용하지 않으며 공유 읽기·최근 15초·말단 256KiB·파일 후보 4,096개 상한으로 제한합니다. UI와 로그 및 Save 전체를 원본의 원자적 명령으로 묶을 수는 없으므로 동시에 발생하는 변경의 모든 경합을 제거했다고 주장하지 않습니다.

M1/S3 각각 실제 `run_ui_session`, Excel 계산기와 native 어댑터를 함께 실행한 2개 시나리오도 통과했습니다. 최소화 상태에서 WebCam→Sequences→WebCam으로 바꾸면서 새 층을 전달해 첫 두 관찰에서 저장 0회, 세 번째 관찰에서 IR62→67 저장 1회를 확인했습니다. 같은 행을 두 번 더 읽어도 추가 저장은 없었고 연결 해제가 완료됐습니다. `background-session-results.json`에 기록했습니다. 기존 13개와 합쳐 제품 경로 통합 시나리오는 총 30개입니다.

## 배경 동작의 적용 조건

최초 자동 적용 연결에서는 기존 Sequences 설정을 감사하고 Process 표를 한 번 준비합니다. 이 준비에서 탭이 전환되며, 원본을 최소화한 상태라면 최소화를 유지합니다. 준비 이후에는 다른 탭으로 이동해도 제어합니다. 조회·미리보기만 사용하는 경우 Process 표가 기존에 생성되어 있어야 합니다.

행이 매우 적어 세로 스크롤 범위가 없는 표는 숨김 갱신을 확인할 수 없어 거부합니다. 이 경우 Process 화면을 보이는 상태로 사용해야 합니다. 원본 UI의 응답 없음, Windows 절전·세션 종료, 서로 다른 권한 수준, 컨트롤 제거 시에는 배경 제어도 계속할 수 없습니다. 원본 UI 스레드를 우회하거나 메모리 읽기·코드 주입으로 이를 대체하지 않습니다.

재현용 소스·별도 시험 EXE·스크립트와 결과 JSON은 배포 폴더 `validation/`에 있습니다. 시험 스크립트는 자신이 시작한 시험 EXE의 PID/HWND만 사용하고 실제 BinderJet 프로세스를 자동 선택하지 않습니다.

## 고장 대응 검토

- UI 작업과 계산은 GUI 스레드 밖에서 수행하고 이벤트 큐와 기록 크기를 제한합니다.
- 같은 Windows 사용자 세션에서 외부 모듈 중복 실행과 중복 연결을 차단합니다.
- 연결 당시의 과거 기록, 중복 기록, 누락/역행 층, 작업 변경을 구분합니다.
- IR의 수동 변경이나 다른 설정 변경이 확인되면 자동 덮어쓰기를 중단합니다.
- 연결 전 저장되지 않은 Sequence 편집값을 저장 항목별로 대조해 거부합니다. M1의 실제 기존 owner 파일에서 필요한 73개 키와 타입을 읽기만 하여 확인했습니다. S3는 74개 항목을 매핑했습니다.
- AUTO/RUNNING을 벗어나거나 상태를 확인할 수 없으면 계산을 멈추고 학습 이력을 초기화합니다. 자동 운전 재개 후에는 기존 행을 기준으로 잡고 새 기록부터 다시 관찰합니다.
- IR 입력 변경 전과 Save 호출 전에 표시를 남깁니다. 이후 시간 초과/취소/확인 실패가 나면 결과 불명확 오류로 중단합니다.
- Save를 자동 재시도하거나 이전 값으로 되돌리지 않습니다. 마지막 저장값은 원본 프로그램에 남습니다.
- 응답하지 않는 도우미만 제한 시간 후 종료합니다. 원본 프로세스에는 종료 명령을 보내지 않습니다.
- 화면 조회는 3초, 연결 준비와 Save 절차는 5초로 제한합니다. 취소 요청은 이 한계와 별도로 도우미 대기 중 확인합니다.
- 보조 코드는 DLL로 미리 빌드해 매 조회의 C# 컴파일을 없앴고, 검증한 컨트롤 HWND를 재사용합니다.
- 설정 파일은 공유 읽기 모드와 크기/파일 수 제한을 사용하여 원본의 원자적 파일 교체를 방해하지 않도록 했습니다.

## 실행 환경과 검증 한계

동봉된 Python/Tk 런타임으로 실행하므로 별도 Python 설치가 필요 없습니다. 원본 프로그램과 동일한 Windows 사용자와 권한 수준에서 실행합니다.

Windows 메시지/MSAA 조회도 원본 UI 스레드의 응답이 필요합니다. 읽기를 최소 1초 간격으로 제한하고 대상과 읽기 크기를 제한했지만 원본 화면 부하가 완전히 0이라고 보장할 수는 없습니다. 원본 표 갱신 주기 약 1초와 도우미 처리 시간이 더해지므로 하드 실시간 제어가 아닙니다.

시험 중 .NET DataGridView의 화면 밖 행 Bounds 계산이 다른 행 Bounds를 연쇄 조회하며 UI 스레드를 점유하는 stack을 확보했습니다. 최종 구조는 폼/표 UIA 트리, 행의 IsOffscreen/Bounds, 전역 FocusedElement를 조회하지 않습니다. 개별 입력/버튼의 AutomationId만 식별한 뒤 그 도우미를 종료하고, 값/IR 입력/Save/현재층 표 조회/화면 복귀는 Windows 메시지와 MSAA로 처리합니다. 다른 앱의 UIA provider를 조회하는 전역 포커스 검사도 제거했습니다.

기존 Save 자체가 여러 설정을 저장하는 절차입니다. 전후 확인과 수동 편집 감지로 경합을 줄이지만, 다른 프로그램/사람이 같은 순간에 설정을 바꾸는 상황까지 원자적으로 잠글 수는 없습니다. 자동 적용 중에는 원본 Process/Sequences 화면을 동시에 편집하지 않아야 합니다.

다른 설정 화면이 원본 프로그램의 메모리에만 보관하는 미저장 값은 외부 UI에서 전부 증명할 수 없습니다. 원본의 다른 설정 화면에도 미저장 편집값이 없는 상태에서 연결해야 합니다. 연결 해제는 이미 원본 UI에 전달된 Save의 취소를 보장하지 않습니다.

실행 중이지 않은 기존 S3 빌드 폴더의 설정에는 현재 소스 매핑 중 9개 항목이 없었습니다. 이런 설정에서는 항목명을 표시하며 자동 적용을 거부합니다. 외부 모듈이 누락 설정을 만들어 넣거나 원본의 Load/설정 복구를 대신 실행하지 않습니다. 실제 S3 실행 환경과의 호환성은 별도로 확인해야 합니다.

실제 운전 중인 장비에 IR 값을 변경하는 시험은 하지 않았습니다. 실제 램프 출력 반영 시점, 열 응답, 장시간 운전 중의 영향은 실장비에서 별도로 확인해야 합니다. 원본의 층별 출력 예약이 있다면 외부 제어와 충돌할 수 있으며 설정 변화 감지 시 외부 제어가 중단됩니다.

원본 공정은 온도 읽기 요청 뒤 현재 온도를 기록하지만, 해당 경로에서 읽기 성공 반환값을 확인하지 않는 부분이 있습니다. 따라서 새 T_Recoating 행이 생겼다는 사실만으로 새 물리 센서 측정의 성공까지 증명할 수 없습니다. 이 모듈은 원본 화면의 새 기록과 설정 저장 결과를 확인하며, 센서 정상 수신이나 실측 램프 출력을 독립적으로 검증하지는 않습니다.

원본 저장소의 추적 소스 변경분은 되돌렸고 Git 상태를 확인했습니다. 독립 모듈 검증 단계에서는 원본 실행 파일을 다시 빌드하거나 교체하지 않았습니다. 초기 방식 검토 중 생성한 기존 빌드 산출물의 과거 바이트 일치 여부까지 검증한 것은 아닙니다.
